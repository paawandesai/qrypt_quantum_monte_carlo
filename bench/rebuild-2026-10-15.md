# Environment rebuild and teardown, 2026-10-15

A throwaway stack (`-var environment=rebuild`, its own Terraform state) was
applied from empty and destroyed in `us-east-1`, using the same account as
`qmc-dev`, so the dev endpoint kept its URL. Terraform 1.16.6, AWS provider
6.69.0, run from a cloud container with the deployer IAM user. Wall-clock
times from `date` around each command; nothing stubbed.

| Step | Result |
|---|---|
| `terraform apply` from empty | 39 resources added in **85 s** (reserved concurrency on: worker 10, api 5) |
| Second `terraform plan -detailed-exitcode` | exit 0, no changes (no drift) |
| `terraform destroy` | 39 resources destroyed in **123 s** |
| Leftovers after destroy | none: no Lambda functions, tables, queues, log groups or code bucket with the stack's prefix |

Not counted: `terraform init`, `scripts/build.py`, and the two SSM parameters,
which are created out of band and survive a destroy on purpose. "From a clean
account" was not tested: the account already had the quota increase, the SSM
parameters and the `bootstrap` stack.

The rehearsal found two bugs before this clean run, fixed in the same MR:

1. Apply from empty failed: creating a NONE-auth Function URL makes AWS add a
   statement named `FunctionURLAllowPublicAccess`, the same id our
   `aws_lambda_permission` used. Ours now use their own ids.
2. Destroy failed: the deployer could not poll `GetEventSourceMapping` for a
   mapping that was already gone (Lambda authorizes that lookup against `*`).
   The deploy policies now grant that read-only action on `*`; see README
   "Known constraints".
